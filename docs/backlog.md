# 동결 목록

지금 하지 않기로 한 것들. **왜 얼렸는지와 무엇이 생기면 녹는지**를 같이 적는다 —
"나중에" 만 적힌 목록은 다음 사람이 우선순위를 다시 처음부터 판단해야 한다.

원장 유지가 이 제품의 해자이므로, 원장 무결성 항목은 UI 보다 위에 둔다.

## A. 원장 무결성 (배치 1 잔여)

### A-1. `seed:301 --dry-run`

**무엇** 쓰기 없이 "적재하려던 행 집합" 만 산출해 현재 DB 와 diff.
비교 축은 행수 · 8자리 코드 집합 · 리스트 배정 · 세율.

**왜 얼렸나** 지금 `seed:301` 을 그냥 돌리면 9,924행을 지우고 다시 넣는다.
그 자체가 사고 위험이라 dry-run 없이는 손대지 않기로 했다. 즉 이건 **다음에
중국 301 을 건드리기 전에 반드시 선행**해야 하는 항목이다.

**녹는 조건** USTR 이 리스트를 개정하거나, 배제(exclusion) 471건을 적재할 때.

### A-2. `ledger.manifest.json`

**무엇** `program_code` 별 행수 + 코드 집합 sha256. **`archive` 섹션을 분리**해
만료 행의 행수·해시를 따로 기록한다 — 만료 행이 사라지면 드리프트로 잡히게.

**왜 얼렸나** 0021·0022 가 들어가면서 급한 불(중복·임의 삭제)은 DB 가 막는다.
매니페스트는 그 위의 탐지 계층이라 우선순위가 한 칸 내려갔다.

**주의** 매니페스트를 뜨기 전에 원장이 정상이어야 한다. 오늘 122 중복을 그대로
두고 해시를 떴다면 **손상된 상태가 정답으로 굳었을** 것이다.

### A-3. 2층 대조

**무엇**
- CI(오프라인): 커밋된 입력(`data/section301_lists.json` 등)에서 매니페스트를
  재생성해 커밋된 것과 비교 — 자격증명 없이 도는 층
- pre-push / SOP: 실제 DB 를 매니페스트와 비교 — 배포본이 도는 층

**왜 두 층인가** CI 는 자격증명이 없어 DB 를 못 본다. DB 를 보는 검사는 사람이
푸시할 때만 돌 수 있다. 한 층만 두면 "코드는 맞는데 DB 가 다른" 상태를 못 잡는다.

### A-4. `ieepa-reciprocal` 소유자 미정

**무엇** 원장에 2행이 있는데 `OWNED` 의 어느 로더에도 속하지 않는다. 즉 어떤
스크립트도 이 행을 재생성할 수 없다 — 지워지면 수기 복구다.

**왜 얼렸나** 소유자를 정하려면 이 프로그램을 계속 유지할지부터 정해야 한다.

**녹는 조건** A-2 매니페스트. 소유자 없는 행이 목록에 그대로 드러난다.

### A-5. 9903.91.xx (2024 4년 재검토 인상) 미적재

**무엇** `data/section301_lists.json` 의 `review_2024_excluded` 30개 코드가 대상인
별개 인상 조항. 원장에 아예 없다.

**지금 상태 — 경고도 없다.** 예전에는 이 코드들이 "301 미해결" 로 잡혀 경고가
나갔지만, 그건 잘못된 분류였다(레거시 301 기준으로는 확인된 0%). 분류를 바로잡으면서
**경고까지 함께 사라졌다.** 즉 이 30개 라인은 지금 조용히 과소계상될 수 있다.

**왜 얼렸나** 제대로 하려면 `duty_programs` 에 별도 프로그램을 만들고 세율·발효일을
원문에서 확인해 적재해야 한다. 라인에 "모름" 을 붙이는 임시방편으로 되돌리면
E-5 에서 없앤 혼동이 그대로 돌아온다.

**녹는 조건** 중국발 선적에서 이 30개 코드가 실제로 나올 때. 또는 A-1 dry-run 작업 시.

## B. 픽스처 제거 (배치 2)

### B-1. 인라인 `LEDGER` 픽스처 → DB 조회

**무엇** `golden-run` · `build-sample-report` · `bench-500` 이 코드에 박힌 원장
사본을 쓴다. DB 조회로 바꾸고, 실패는 명시적 실패(폴백 금지).

**왜 중요한가** 지금 골든 점수는 **픽스처를 잰 값**이지 프로덕션을 잰 값이 아니다.
둘이 갈라지면 골든은 통과하는데 사용자는 틀린 숫자를 본다 — 이 저장소에서
정확히 그 일이 있었다(재시도 프롬프트가 배포본에서만 죽어 있었고, 러너가 자기
사본을 써서 못 잡았다).

**동결 유지 (2026-07-30 결정)** 논리는 맞지만 지금은 유료 고객이 0명이고,
프로덕션 경로는 `/hts` 라이브 조회로 직접 확인된다 (6912.00.44 CN → 22.5% 실측).
즉 "픽스처와 프로덕션이 갈라졌는지" 를 사람이 눈으로 대조할 수 있는 상태다.

**녹는 조건** 유료 고객 발생. 그 시점에 **1순위로 올린다** — 눈으로 대조하는
방식은 고객 수에 비례해 무너진다.

### B-2. Edge vs 앱 동등성 테스트 (골든 5건)

**무엇** 같은 입력에 두 경로가 같은 숫자를 내는지.

**왜 얼렸나** `resolvePrograms` · `getFees` 를 공유하도록 이미 고쳤으므로 구조적
위험은 낮아졌다. 다만 **공유했다는 사실 자체가 검사되고 있지는 않다** — 누가
Edge 쪽에 자체 쿼리를 다시 짜 넣으면 조용히 갈라진다.

## C. UI

### C-1. `/section-301` 페이지 — **완료 (2026-07-30)**

검색량 1천~1만 키워드가 이미 캠페인에 있는데 전용 페이지가 없어서 홈으로
떨어지고 있었다. 클릭마다 손해라 앞당겼다.

**유지보수 지점 하나**: 리스트별 8자리 라인 수가 페이지에 하드코딩돼 있다
(as-of 날짜를 같이 적어 뒀다). A-2 매니페스트가 생기면 그 값과 대조해야 한다 —
지금은 원장이 바뀌어도 페이지가 따라가지 않는다.

### C-2. `/hts/:code` 딥링크 SEO

**무엇** 지금은 클라이언트에서 경로를 읽어 조회한다. 크롤러에 코드별 페이지로
잡히려면 정적 생성(코드당 HTML)이 필요하다.

**왜 얼렸나** 27,000 페이지를 찍는 일이라 인덱싱 정책부터 정해야 한다.

**정책 완료 (2026-08-01)** [seo-indexing-policy.md](seo-indexing-policy.md) 에
정했다. 발행 단위는 8 자리(11,319 장), 원산지는 URL 이 되지 않는다, 세율
미확정·설명 빈약 라인은 noindex, 200 → 1,000 → 5,000 → 나머지 웨이브로 나눠
Search Console 색인률 게이트를 통과해야 다음이 나간다. 판정은
`src/lib/seo/pages.ts` 에 코드로 있고 `tests/seo.pages.test.ts` 가 경계를 고정한다.

정책을 정하면서 드러난 사실 하나: 지금 막고 있는 건 크롤링이 아니라 `hts.html`
머리의 **고정 canonical** 이다. 하위 경로가 전부 `/hts` 로 합쳐지도록 우리가
선언하고 있다.

**녹는 조건** 셋 남았다 — (1) A-2 매니페스트, (2) 웨이브 1 의 200 코드 선정
(광고 검색어 리포트 · Search Console · `leads.page`), (3) `hts.html` 폴백
noindex·canonical 수정.

**A-2 가 이것보다 먼저다.** 지금 원장 오류의 폭발 반경은 "사용자 한 명이 틀린
숫자를 본다" 이지만, 발행 후에는 "11,000 개 공개 페이지가 틀린 채로 구글에
캐시된다" 가 된다. 되돌리는 비용이 비대칭이라 탐지 계층이 발행보다 앞선다.

## D. 운영 · 사용자 작업

### D-1. Google Ads 신원확인 제출 — **사용자**

푸터 3값(상호·주소·이메일)은 이미 들어갔다.

### D-2. Google Ads 전환 라벨

**끝났다.** 라벨·중복방지는 `public/ads.js` 한 곳, 모든 폼이
`window.trackConversion(...)` 하나를 부른다.

전환 액션은 **하나만 쓴다.** 입찰이 클릭수 최대화라 액션을 세분화해도 최적화에
쓰이지 않고, 유입 경로 구분은 `leads` 테이블의 UTM + `page` 로 이미 한다.
액션을 늘리면 라벨 관리 지점만 늘어난다.

### ID-only 전송 경로는 제거했다

`send_to` 에 ID 만 넣으면 어느 전환 액션에도 매핑되지 않아 **기록 자체가 안 된다.**
"액션 구분만 빠진다" 가 아니다. 리포트에는 전환 0 으로만 보이고 태그는 정상
동작 중이라 원인을 찾을 단서가 없다.

라벨이 비면 전송하지 않고 `console.error` + Plausible `ads_label_missing` 을
남긴다 (콘솔은 아무도 안 본다 — 우리가 보는 대시보드에 찍혀야 발견된다).
`check:build` 가 두 라벨이 비었는지, ID-only 경로가 되살아났는지 검사한다.

### 남은 확인 — 사용자

배포 후 Google Ads → 목표 → 전환에서 **"태그 감지됨"** 으로 바뀌는지
(몇 시간~하루). 안 바뀌면 라벨이 아니라 태그 적재를 의심할 것.

### 아직 전환을 보내지 않는 경로

`/app` 의 가입(AuthPage)은 `trackConversion` 을 부르지 않는다. 랜딩 폼 제출과
실제 계정 생성이 같은 사람의 두 단계라 둘 다 세면 한 사람이 2건이 된다.
붙일지는 유료 전환이 생긴 뒤에 판단한다.

### D-3. 데모 영상 캡처

`scripts/record-demo.ts` 가 선적 생성 셀렉터에서 막혀 있다.

## E. 알려진 한계 (고칠 대상이 아니라 아는 대상)

### E-1. `TRUNCATE` 는 아카이브 트리거를 우회한다

행 트리거는 `TRUNCATE` 에 걸리지 않는다. 0022 는 **실수 방지 장치이지 권한
통제가 아니다.** 권한으로 막으려면 서비스 롤을 나눠야 한다.

### E-2. 면제 우선순위 — 확인·미확인 중첩

`exclusionStatus` 는 confirmed 가 하나라도 있으면 confirmed 로 본다. 배제 471건을
적재하면 **8자리 confirmed 가 넓게 덮고 10자리 unverified 가 좁게 겹치는** 경우가
생긴다. 그때는 좁은 쪽이 이겨야 한다. 코드에 TODO 로 표시돼 있다.

**녹는 조건** A-1 dry-run → 배제 471건 적재.

### E-4. note 행수 vs 실제 행수 — **설명됨 (2026-07-30)**

차이는 오류가 아니라 **note 20 이 열거하는 코드 중 현행 관세표에 없는 것들**이다.
계산으로 정확히 맞는다:

| 리스트 | note | 현행 카탈로그에 있는 것 | 차이 |
|---|---|---|---|
| List 1 | 856 | 856 | 0 |
| List 2 | 283 | 283 | 0 |
| List 3 | 5,906 | 5,899 | −7 |
| List 4A | 2,958 | 2,886 | −72 |

합계 9,924행 — DB 실측과 일치한다. 로더가 이 숫자를 콘솔에 남기도록 고쳤다.
조용히 사라지면 나중에 "왜 안 맞지" 로 돌아온다.

### E-5. `301-china-unverified` — **해결, 미해결 0건 (2026-07-30)**

구조(0023, 3값)와 데이터를 둘 다 끝냈다. 5행은 Note 20 에서 형제 코드를 찾아
확정했고 근거가 두 갈래로 갈렸다:

**시계 3건** (9105.19.40 · 9105.29.40 · 9105.99.50) — Note 20 이 **List 4B 로 직접
열거**하고 있었다. 4B 는 정지 목록이라 부재가 곧 확인된 0% 다. 로더의 형제 규칙이
직접 열거를 덮어쓰는 버그였다 — 정지 목록에 열거된 것은 "모르는" 게 아니라
"0% 임이 확인된" 것이다. 규칙에 `enumeratedAnywhere` 차단을 넣었다.

**2건** (4015.12.10 · 8426.19.00) — 레거시 리스트(1·2·3·4A·4B) 어디에도 없다.
열거되지 않았으므로 not_covered, 확인된 0% 다. 이 둘이 미해결로 잡혀 있던 이유는
9903.91.xx(2024 4년 재검토 인상) 대상이기 때문인데, 그건 **별개 조항**이다 →
A-5 로 옮겼다. 라인 단위 "모름" 과 프로그램 단위 공백을 섞으면 진짜 모르는
라인과 구분이 안 된다.

고친 로더를 오프라인으로 재현해 DB 와 대조했다: 9,924행 / 미해결 0건, 일치.

### E-3. FY2027 전환 (2026-10-01)

MPF 상·하한이 바뀐다. 그날 전에 `fee_settings` 에 새 행을 넣고 직전 행을 닫아야
한다. **닫기 → 삽입 순서**여야 한다 (`fee_settings_one_open` 이 non-deferrable).
SOP §3 에 날짜 체크로 들어가 있다.
